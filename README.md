# CQA: оценка качества диалогов операторов

## Команда

Utopia

## О проекте

Прототип системы Conversation Quality Analytics для Freedom Broker: ИИ оценивает
чаты и звонки операторов по чек-листу из 8 критериев, объясняет каждое решение ссылками на реплики,
считает итоговый балл, отмечает грубые ошибки и даёт оператору оспорить оценку.

**Результаты:** [`results/dev/results.json`](results/dev/results.json) (65 диалогов DEV),
`results/prod/results.json` (контрольный набор, появится в финальный час).

## Главное

| | |
|---|---|
| Точность на нашем эталоне (24 диалога DEV, чаты) | **95%** критериев совпали (168/176) |
| Грубые ошибки | **100%** найдены верно (24/24), ложных срабатываний на эталоне нет |
| Стоимость | ~$0.006 на диалог (Claude Haiku 5.5 + второе мнение), 65 диалогов DEV - $0.38 |
| Время | ~30 с на диалог в облаке, 10 контрольных чатов - 2 мин 47 с с загрузкой и проверкой формата |
| Режимы | облако, локальная модель (данные не покидают компанию) и гибрид с автоматическим переходом |
| Чек-лист | редактируется в интерфейсе; после правки ИИ переспрашивается только по изменённым критериям |

## Как это работает

```
API хакатона / JSON / вставленный текст
        │
        ▼
  1. Факты считает код (backend/facts.py)
     нумерация реплик, время первой реакции оператора (SLA 3 мин), системные события
     (идентификация пройдена, перевод, обрыв связи), язык. ИИ не нужно считать минуты.
        │
        ▼
  2. Промпт собирается из чек-листа (backend/prompt.py)
     критерии, ступени шкал, правила N/A и общие правила толкования берутся из JSON чек-листа.
     В коде нет ни одного конкретного критерия: замените чек-лист - изменится и промпт.
        │
        ▼
  3. Ответ ИИ в JSON → проверка (backend/validator.py)
     по каждому критерию: ответ, номера реплик-доказательств, объяснение, уверенность.
     Нет такой реплики, N/A там, где он запрещён, балл не из шкалы → модель получает
     список ошибок и отвечает заново.
        │
        ▼
  4. Устойчивость (backend/evaluator.py)
     спорные шкалы (консультация, ведение диалога) спрашиваются 3 раза, берётся медиана.
     Найденную грубую ошибку перепроверяет более сильная модель (второе мнение).
        │
        ▼
  5. Баллы считает код, не ИИ (backend/scoring.py)
     итог = сумма баллов применимых критериев / сумма их весов × 100;
     N/A исключается из знаменателя; округление половины вверх до 2 знаков.
        │
        ▼
  SQLite (история оценок, версии чек-листа, апелляции) → API (FastAPI) → интерфейс
```

### Второе мнение по грубым ошибкам

Ложная грубая ошибка - самое дорогое, что может сделать система: оператора наказывают за то, чего не было.
Поэтому если основная модель (Haiku) ставит грубую ошибку, отдельный запрос отправляется более сильной
модели (Claude Sonnet 5.5) - только по этому критерию этого диалога.

- Согласна - ошибка подтверждена двумя моделями.
- Не согласна - берётся её ответ, диалог помечается «Нужна проверка», в карточке видны оба объяснения.
- Недоступна - остаётся первый ответ, оценка не падает.

Пример: в p4-ru-004 Haiku поставил «раскрыл данные счёта без идентификации», хотя данных раскрыто не было.
Второе мнение не согласилось, ложная грубая ошибка снята. Дополнительная стоимость - около $0.015 только на
диалоги с грубой ошибкой (8 из 65 в DEV).

### Модели: облако, локально и гибрид

Модель задаётся одной строкой в `.env` (через LiteLLM), без изменения кода. Цепочка по умолчанию:

```
Claude Haiku 5.5 (облако, основная) → Groq gpt-oss-120b (облако, бесплатный резерв) → Gemma 4 E4B (локально, Ollama)
```

Ограничение «в минуту» - программа ждёт и повторяет ту же модель. Дневной лимит, отказ провайдера или
слишком большой запрос - сразу переходит к следующей. Если облако недоступно полностью, оценка всё равно
будет получена на ноутбуке. Поле `model.mode` в файле сдачи (`local` / `external_api` / `hybrid`)
определяется по фактически использованным моделям.

Измерено на одних и тех же 23 диалогах эталона:

| | Локально: Gemma 4 E4B | Облако: Claude Haiku 5.5 |
|---|---|---|
| Критерии совпали, чаты | 87% (146/168) | 96% (161/168) |
| Грубые ошибки | 100% (23/23) | 100% (23/23) |
| Итог совпал точно | 35% | 70% |
| Время на диалог | ~5.5 мин (ноутбук, RTX 3050 4 ГБ) | ~30 с |
| Стоимость | $0, данные не покидают компанию | ~$0.006 |

Локальный режим - для банка, которому нельзя отправлять переписку клиентов во внешние сервисы:
грубые ошибки ловятся так же надёжно, по оценочным критериям точность ниже. На сервере с нормальной
видеокартой и моделью покрупнее разрыв сократится; код менять не нужно.

## Точность: как мы её измеряли

Качество оценки определяется совпадением ответов с эталоном по каждому критерию. Чтобы измерять его
с первого дня, мы сами разметили 24 диалога DEV (RU, KZ, EN; 22 чата и 2 звонка) -
[`data/answer_key/draft.json`](data/answer_key/draft.json). Для каждого ответа записано обоснование
([`review.md`](data/answer_key/review.md)) и расчёт итога ([`calculations.md`](data/answer_key/calculations.md)).
Спорные места сверены с официальными разъяснениями к заданию и сведены в
[`docs/rules.md`](docs/rules.md).

**Эталон используется только для измерения.** Оценщик его не видит и не загружает: ответы получаются
от ИИ на каждом прогоне (`eval/run_answer_key.py` сравнивает их с эталоном уже после). Правила толкования
записаны в инструкции чек-листа и действуют для любого диалога, а не для конкретных номеров.

Результат Claude Haiku 5.5 (повторный опрос + второе мнение):

| Критерий | Точность | | Язык | Точность |
|---|---|---|---|---|
| Установление контакта | 100% | | RU | 95% |
| Выявление потребности | 92% | | KZ | 100% |
| Идентификация | 96% | | EN | 92% |
| Консультация (шкала 0-20) | 79% | | | |
| Эмпатия | 100% | | | |
| Ведение диалога (шкала 0-10) | 75% | | | |
| Завершение | 100% | | | |
| Грубые ошибки | 100% | | | |

Все 8 оставшихся расхождений на чатах - соседняя ступень шкалы (например, 15 вместо 20), в 6 из 8 модель
строже эталона. Путаницы «применим / не применим» нет.

Как мы шли к этому числу: 91% (Groq gpt-oss-120b) → 93% (правило для консультации: 15 только если можно
назвать конкретную недостающую деталь) → 95% (повторный опрос по шкалам) → правило об оскорблениях
сделало грубую ошибку в p1-ru-029 стабильной на разных моделях. Каждое правило - общее и записано в чек-листе.

### Ключевые правила толкования (по официальным разъяснениям)

- Выявление потребности - N/A, если клиент сразу дал всё нужное и оператор ответил без уточнений.
- Нахождение клиента в приложении - не идентификация (омниканальность).
- Данные счёта без идентификации - и «идентификация: нет», и грубая ошибка.
- Завершение: одно «до свидания» без предложения помощи - «нет».
- Не выдумывать факты: оценивается только то, что есть в диалоге.
- Оскорбление - унизительная оценка личности или грамотности клиента (в том числе риторический вопрос
  «Вы вообще читать умеете?»); просто резкий тон - не грубая ошибка, а минус по эмпатии.

## Возможности для пользователя

Интерфейс - один HTML-файл без внешних зависимостей ([`frontend/index.html`](frontend/index.html)),
открывается по адресу `http://localhost:8000/ui/`. Языки: русский, казахский, английский.

| Задача | Где |
|---|---|
| Все диалоги с грубыми ошибками и причинами | список → вкладка «Грубые ошибки»; в карточке красная плашка с объяснением |
| Оценка диалога с объяснениями | клик по диалогу: по каждому критерию ответ, баллы, объяснение, ссылки на реплики (#12 - наведите, увидите текст) |
| Что видел ИИ | «Технические детали»: модель, токены, стоимость, факты, посчитанные кодом |
| Звонки | плеер записи; клик по реплике - перемотка на её момент |
| Апелляция | оператор оспаривает критерий с комментарием → проверяющий принимает или отклоняет; итог пересчитывается сразу, исходный ответ ИИ сохраняется |
| Изменить чек-лист | вкладка «Чек-лист»: добавить или изменить критерий, вес, шкалу, инструкцию для ИИ; проверка, что веса дают 100 |
| Переоценка | после правки - таблица «было → стало» по каждому диалогу; ИИ переспрашивается только по новым и изменённым критериям (3 диалога - 11 с и $0.0013), смена одного веса пересчитывается вообще без ИИ |
| Нужна проверка | диалоги, где ИИ не уверен (уверенность < 0.7) или модели разошлись |
| Загрузка данных | «Данные ▾»: из API хакатона, вставленный текст, JSON или CSV |

**Встраивание в Dynamics 365:** файл подключается как веб-ресурс; параметры адреса открывают нужное:
`?conversation_id=p1-ru-001` - карточка диалога, `?page=checklist|appeals`, `?lang=kz`, `?role=operator`.

Каждая версия чек-листа хранится: оценка всегда ссылается на версию, по которой она сделана.

## Запуск

```bash
pip install -r requirements.txt
cp .env.example .env            # Windows: copy .env.example .env; впишите адрес API хакатона и ключ
uvicorn backend.main:app        # интерфейс: http://localhost:8000/ui/   API: http://localhost:8000/docs
pytest                          # 114 тестов, без вызовов модели
```

Минимум для `.env`: `CQA_ORG_API_URL`, `CQA_MODEL` и ключ этого провайдера. Все настройки описаны в
[`.env.example`](.env.example). Полностью локально: `ollama pull gemma4:e4b`, затем
`CQA_MODEL=ollama_chat/gemma4:e4b`.

### Файл сдачи

```bash
python -m eval.make_results --group DEV            # 65 диалогов -> results/dev/results.json
python -m eval.make_results --group PROD           # контрольные чаты -> results/prod/results.json
python -m eval.make_results --group PROD --check   # проверить формат готового файла
```

Скачивает набор из API, оценивает действующей версией чек-листа, пишет файл по формату приложения
(коды критериев, true/false/null, реплики с 1, записи с ошибкой) и проверяет его. Повторный запуск доделывает
только упавшие диалоги; после замены критерия - переспрашивает только его. Порядок финального часа:
[`docs/final_run.md`](docs/final_run.md).

### Измерение точности

```bash
python -m eval.run_answer_key                       # прогон по эталону: отчёт по критериям и языкам
python -m eval.run_answer_key --ids p1-ru-001,p1-kz-003
```

## Ограничения

- Шкалы «Консультация» и «Ведение диалога» - самые спорные (75-79%): ошибки на соседней ступени, и даже
  люди расходятся на них чаще всего. Такие случаи система чаще отправляет в «Нужна проверка».
- Звонки: точность ниже (62% на 2 звонках эталона) - расшифровка с ошибками распознавания и
  без пунктуации. Контрольный набор - только чаты.
- Эталон размечен нашей командой: это лучшая доступная нам оценка, но не официальный эталон.
- Исходные данные (`data/raw/`) и ключи в репозиторий не попадают.
